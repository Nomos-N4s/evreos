# Tasks: Evreos v1

**Input**: design documents in `/specs/001-evreos-v1/` — all merged to `main`.

**Tests**: every task that lands behaviour lands its tests with it. There is no testing phase,
because a testing phase is where tests go to be cut.

**Organization**: grouped by user story, so each can be implemented, tested and delivered
independently.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: may run in parallel — different files, nothing incomplete depended on
- **[Story]**: `[US1]`, `[US2]`, `[US3]`; absent in Setup, Foundational and Polish
- Every task names the exact file paths it touches

## Three constraints that govern the ordering

**T014 revises the `Engine` trait, and every platform backend is ordered behind it.**
`research.md` establishes the merged trait cannot be implemented on either shipping backend:
`load` is synchronous while WebView2 is UI-thread-affine and wry's macOS delegates are
`MainThreadOnly`, so the only synchronous route is a nested message pump that breaks SC-006 by
construction. And `Result<Page, LoadError>` cannot express engine-initiated navigation, in-flight
state, or a title arriving on its own event.

**T013 procures the two pinned reference machines, and every measurement is ordered behind it.**
A figure measured on an unnamed machine is not reproducible under SC-013, so it cannot be what a
build fails on.

**T016 records ADR-0002, and nothing that renders chrome is ordered ahead of it.**
`plan.md` carries the windowing crate and what renders the chrome as spike S4 and marks it NEEDS
CLARIFICATION; `research.md` names three candidates with different costs. Until that ADR exists
there is no windowing API for a task to call, so the crate that renders the chrome surfaces, the
focus-boundary work and the dead-key and Greek text-entry test all cite the ADR rather than naming
an API of their own. T015 measures N6 first, because a negative screen-reader result at the
chrome/content boundary eliminates the drawn-chrome candidate under Principle X rather than costing
it.
